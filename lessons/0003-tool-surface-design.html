Designing a Tool an Agent Can Use

Your agent is only as good as the surface it acts through. This lesson is about the part most people treat as plumbing and Anthropic treats as prompt engineering: the tool definition itself.

The schema is the model's whole world

In Lesson 01 you wrote a function, added it to TOOLS, and watched the agent ignore it — because the schema never made it into TOOL_SCHEMAS. That bug has a lesson in it bigger than the fix. The model has no access to your code. It cannot read the function body, the docstring, the types, or the tests. Everything it knows about what it can do comes from the name, the description, and the parameter schema you sent.

Which means those fields are not documentation. They are prompt — a section of the prompt you happen to write in JSON. Anthropic is explicit that prompt-engineering the descriptions is "one of the most effective methods for improving tools", and reports that precise refinements to tool descriptions alone were enough to take Claude Sonnet 3.5 to a state-of-the-art result on SWE-bench Verified. No model change. Better tool text.

The surface as a whole — names, schemas, descriptions, and the text your tools return — has a name worth using in a design review: the ACI, the agent–computer interface. The analogy is load-bearing. You would not ship a human UI without design effort; this is the agent's UI, and Anthropic argues it deserves as much investment as the human-facing one.

The reframe

Stop asking "what functions does my service have?" Start asking "what would a capable new colleague need, on their first day, to finish this task?" Everything below follows from taking that question literally.

1. Design for the task, not for the API

The default move is to wrap each endpoint in a tool. It feels principled — thin, complete, no opinions. It is also the most reliable way to build an agent that burns twenty thousand tokens finding a customer's email address.

Anthropic's guidance is blunt about it: "More tools don't always lead to better outcomes." The examples are worth memorising because they are all the same move — collapse a sequence a human would perform into one tool:

Instead ofBuildBecause
list_users, list_events, create_event schedule_event Three round trips and two intermediate result sets collapse into one
read_logs search_logs Filtering happens before the context window, not inside it
get_customer_by_id, list_transactions, list_notes get_customer_context The agent never needed the pieces — it needed the picture

This is not an argument for one giant tool. The test is whether the grouping matches how the work is actually done: tools should "enable agents to subdivide and solve tasks in much the same way that a human would". If a human support agent would always pull orders and tickets together, that is one tool. If they would sometimes want only the billing history, that is a second.

When you do have many tools, namespace them — asana_search, jira_search, or asana_projects_search, asana_users_search. Anthropic found that even the choice between prefix and suffix had "non-trivial effects on tool-use evaluations", which tells you how thin the margins are here.

2. Return what a colleague would read

The second half of the surface is the half people forget: what comes back. A tool result is text you are inserting into the model's context, and it competes for the same attention as everything else there.

Endpoint-shaped result

{
  "uuid": "7f3c9a1e-4b82-...",
  "owner_uuid": "a91f-...",
  "mime_type": "image/png",
  "256px_image_url": "...",
  "status_code": 3
}

Agent-shaped result

{
  "name": "Q3 revenue deck",
  "owner": "Priya Raman",
  "file_type": "image",
  "image_url": "...",
  "status": "awaiting review"
}

The claim is stronger than "it reads nicer". Anthropic reports that merely resolving arbitrary alphanumeric UUIDs into semantically meaningful language "significantly improves Claude's precision in retrieval tasks by reducing hallucinations". An opaque identifier is a token sequence with no meaning to reason over; a name is evidence. Keep the identifiers when a later tool call genuinely needs them — just stop making them the whole payload.

That last tension has a clean solution worth stealing: give the tool a response_format parameter with "concise" and "detailed" values, and let the agent choose. In Anthropic's Slack example the detailed version of a thread cost 206 tokens against the concise version's 72 — roughly a third of the context for the same answer.

3. Put a ceiling on it, and say so

Any tool that can return a list can return ten thousand rows, and the model cannot defend itself against that. So the tool has to: Anthropic recommends "pagination, range selection, filtering, and/or truncation with sensible default parameter values", and notes that Claude Code caps tool responses at 25,000 tokens by default.

The part that separates a working surface from a merely safe one is what you say when you truncate. A silent cut produces a confident answer built on a third of the data. A cut that speaks does not:

# Silent — the agent cannot tell this happened.
return rows[:50]

# Steering — states the limit, and names the cheaper strategy.
return (
    f"Showing 50 of {total} matches. "
    f"Narrow with date_from/date_to or a more specific query "
    f"rather than requesting the full set."
)

Anthropic's framing: when truncating, steer the agent toward "more token-efficient strategies, like making many small and targeted searches instead of a single, broad search."

Deliberately not in this lesson

Error messages — what a tool says when it fails — are the other half of this and are Lesson 04's entire subject. Today is about the happy path: the definition the model reads, and the result it gets back when things work.

The checklist

Five questions. They are the whole lesson, and they are what you run over any tool before it ships. The reference card has them with examples.

  1. Task or endpoint? Does this tool match a step a human would take, or a row in your API docs?
  2. Could a new colleague use it from the description alone? Implicit context made explicit, niche terms defined, relationships between resources spelled out.
  3. Is every parameter name unambiguous? user_id, not user. The type does not say which one you meant; the name does.
  4. Is the result high-signal? Semantic names over identifiers, and a verbosity control if both are genuinely wanted.
  5. What happens at ten thousand rows? A default limit, and a truncation message that tells the agent what to do instead.

Build it

Same shape as last lesson: produce a number. You are given a deliberately endpoint-shaped tool surface over a small support dataset. You will measure it, redesign it, and measure again.

Your task, about 12 minutes

Everything is in practice/03-tool-surface/. Run with uv run python practice/03-tool-surface/<file>.py.

  1. Predict first. Open naive_tools.py and read the four tool definitions and data.json. Before running: how many tool calls will the agent need to answer "Has Priya Raman had an order delayed, and is there an open ticket about it?" Write the guess in NOTES.md.
  2. Run it. It prints the tool calls in order, plus API calls and token totals.
  3. Write good_tools.py: the same question, the same loop, but one tool you design yourself. Run the checklist over it before you run the file. Semantic fields, no raw UUIDs in the result, a documented default limit.
  4. Compare tool calls, API calls, and input tokens. Write both sets in NOTES.md.
  5. Then find the cost. Ask both surfaces a question your consolidated tool cannot answer but the endpoint-shaped one can. Write down what each did. Consolidation buys tokens and spends flexibility, and you should be able to say what you spent.
One confound to keep in mind

The practice files use claude-haiku-4-5 for cost, as your Lesson 01 agent does. The token arithmetic holds on any model, but how well a model copes with a bad tool surface is model-dependent — a stronger model papers over more of it. If a result surprises you, re-run that one on claude-sonnet-5 before drawing a conclusion.

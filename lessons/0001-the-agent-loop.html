The Agent Loop

An agent is not a model. It is a loop you own, and once you can write it from memory, every framework you meet becomes readable.

Lesson 01· AI Agents· about 25 minutes

You have called an LLM API. You send messages, you get text back, the call ends. That is a function. This lesson turns it into an agent by adding the one thing it lacks: the ability to act, see what happened, and decide what to do next.

The gap is smaller than the discourse suggests. Anthropic's own framing is blunt about it. Agents are "just LLMs using tools based on environmental feedback in a loop." Everything else you will learn in this course (tools, memory, guardrails, evals) hangs off the skeleton you build in the next twenty minutes.

The four moving parts

An agent loop has exactly four. Nothing in a production agent is a fifth thing; it is one of these four, elaborated.

PartWhat it isWho owns it
The transcript A growing messages list, re-sent in full on every iteration You
The tool schemas Named, typed capabilities the model may request You
The branch stop_reason: continue looping, or stop The model decides, you obey
The dispatch Running the requested tool and feeding the result back You
The idea worth keeping

The model never runs anything. It emits a request, a tool_use block, and then stops generating and waits. Your code, the harness, decides whether that request actually happens.

This is not a technicality. It is the entire basis of agent security, permissioning, and human-in-the-loop approval, which we cover in later lessons. The model proposes; the harness disposes.

The loop, in full

Here is the whole thing. Forty lines, no framework, no abstraction. Read the stop_reason branch first. It is the spine; everything else is plumbing.

import anthropic

client = anthropic.Anthropic()

# 1. THE TOOL SCHEMAS — what the model is allowed to ask for.
#    The description is prompt, not documentation. The model reads it.
TOOL_SCHEMAS = [{
    "name": "get_weather",
    "description": "Get current weather for a city. Returns temperature, "
                   "conditions, and wind speed.",
    "input_schema": {
        "type": "object",
        "properties": {
            "location": {"type": "string",
                         "description": "City name, e.g. Paris"},
        },
        "required": ["location"],
    },
}]

# 2. THE DISPATCH TABLE — your side of the contract.
def get_weather(location: str) -> str:
    return f"8°C, light rain, wind 20km/h in {location}"

TOOLS = {"get_weather": get_weather}


def run_agent(user_input: str) -> str:
    # 3. THE TRANSCRIPT — the agent's entire within-run memory.
    messages = [{"role": "user", "content": user_input}]

    while True:
        response = client.messages.create(
            model="claude-opus-5",
            max_tokens=16000,
            tools=TOOL_SCHEMAS,
            messages=messages,
        )

        # 4. THE BRANCH — the model decides whether the loop continues.
        if response.stop_reason != "tool_use":
            break

        # Append the assistant turn VERBATIM — tool_use blocks intact.
        messages.append({"role": "assistant", "content": response.content})

        # Execute every requested tool. Claude may request several at once;
        # all their results must come back in ONE user message.
        results = []
        for block in response.content:
            if block.type == "tool_use":
                try:
                    output = TOOLS[block.name](**block.input)
                    results.append({"type": "tool_result",
                                    "tool_use_id": block.id,
                                    "content": output})
                except Exception as e:
                    # Errors go BACK to the model, not up the stack.
                    results.append({"type": "tool_result",
                                    "tool_use_id": block.id,
                                    "content": f"Error: {e}",
                                    "is_error": True})

        messages.append({"role": "user", "content": results})

    return next(b.text for b in response.content if b.type == "text")
On that last except

Catching the exception and handing the message back to the model is not sloppiness. It is the design. A tool failure is information the agent can act on: retry with different arguments, try another route, or tell the user it cannot be done. Raising instead would kill a run that the model could have recovered. Lesson 04 is entirely about writing error messages an agent can actually use.

Three traps

These are the three that cost people an afternoon each. They are worth more to you as recognised shapes than as memorised rules.

Trap 1: appending text instead of content

messages.append({"role": "assistant", "content": response.text})

Extracting the text throws away the tool_use block. The tool_result you send next references a tool_use_id that no longer exists in the transcript, and the API rejects the request. Always append response.content, the list, unchanged.

Trap 2: splitting parallel tool results

Claude can request several tools in one response. If you append each tool_result as its own user message, the API may tolerate it, but you have quietly taught the model to stop making parallel calls, and your agent gets slower for reasons that never show up in a stack trace. All results from one assistant turn go in one user message.

Trap 3: while True with no ceiling

The loop above is honest teaching code and unfit for production. A model that misreads a tool result can call the same tool forever, and each iteration costs money. Every real agent has a maximum-iteration guard. Add one before you ship anything.

Recall it cold

Close the tab in your head. Without scrolling up, write the loop's control flow, not the full code, just the sequence of decisions and appends.

Write it from memory
Reveal the answer once you have written something
  1. messages = [user input]
  2. Loop: send the whole transcript + tool schemas
  3. If stop_reason != "tool_use" → break
  4. Append response.content verbatim as the assistant turn
  5. Run every requested tool; collect all results
  6. Append them as one user message of tool_result blocks
  7. Repeat

If you got the order right but missed "verbatim" or "one message", that is the useful gap. Those are traps 1 and 2.

Build it

Your task, about 10 minutes

Type the loop out yourself. Not copy-paste: typing it is part of the exercise.

  1. pip install anthropic, and set ANTHROPIC_API_KEY.
  2. Write the loop above with two tools instead of one. Add a get_time(timezone) alongside get_weather. Fake both; returning a hardcoded string is fine. The tools are not the point.
  3. Add a print() at the top of each iteration showing the iteration number and response.stop_reason. Watch the loop turn.
  4. Ask it something that needs both tools at once: "What's the weather in Tokyo and what time is it there?" Note whether Claude requests them in one response or two.
  5. Now break it on purpose: change the append to response.text and read the error. Seeing trap 1 fire is worth more than being warned about it.
Worth knowing, deliberately skipped

The Python SDK ships client.beta.messages.tool_runner(), which writes this loop for you from decorated functions. It is the right choice for production. You are learning the manual loop first on purpose: your mission is to be the person who can debug the abstraction, and that means having built the thing underneath it once. We will come back to the runner.

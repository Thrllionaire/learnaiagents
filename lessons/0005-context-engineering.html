One window, two different failures

You already know the window has a cost — Lesson 02 put a number on it. What that lesson didn't say is that the same growth curve produces a second, unrelated failure, and confusing the two will cost you a debugging session later.

Anthropic's context engineering guidance opens with the constraint plainly: “context must be treated as a finite resource with diminishing marginal returns” — and names the mechanism: “LLMs are based on the transformer architecture, which enables every token to attend to every other token across the entire context. This results in n² pairwise relationships for n tokens.” Every token you add doesn't just cost tokens — it dilutes the model's attention over every other token already there.

Context rot
new to this lesson		 Nothing you can see in the bill Recall accuracy. The docs name it directly: “as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases.”

These are not the same failure. A run can be cheap and still wrong — a short window stuffed with low-signal tokens rots fast. A run can be expensive and still right — a long transcript of nothing but high-signal turns holds up. The token count on your invoice tells you about the first row. It tells you nothing about the second, which is why "just watch the token count" is not a context strategy.

Working memory, not storage

The analogy the docs reach for is deliberate: “Like humans, who have limited working memory capacity, LLMs have an ‘attention budget’.” A bigger context window (Claude's is large) raises the ceiling. It does not change the shape of the problem — a bigger desk still gets buried if you never clear it.

The rule that scales up

Lesson 03 taught you to write tool results in the model's vocabulary — names and dates, not UUIDs and epoch milliseconds — because high-signal context is easier to reason over and, it turned out, cheaper per character too. Context engineering is that same judgement applied to everything in the window, not just what a tool hands back:

“Good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome.” — Effective context engineering for AI agents

Notice what this is not: it is not prompt engineering. The same source draws the line precisely — prompt engineering is about how you phrase a fixed set of instructions; “context engineering refers to the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference.” Prompt engineering is what you write once. Context engineering is what stays, turn after turn, as the run gets longer than you planned for.

Four ways to keep the window small

For a short run — the two- and five-call agents you've built so far — none of this matters; the window never gets big enough to rot. It matters once a run goes long: a multi-hour coding session, a research agent chasing sources for twenty minutes, anything with more turns than you can eyeball. Four named techniques, each trading something specific for window space.

TechniqueWhat it doesWhat it costs
Compaction “taking a conversation nearing the context window limit, summarizing its contents, and reinitiating a new context window with the summary” Whatever the summary drops. A lossy operation, on purpose — you are choosing what to forget.
Structured note-taking
agentic memory		 The agent “regularly writes notes persisted to memory outside of the context window” — a scratchpad file, not a summary of the transcript Discipline. The agent has to be prompted to write the note before it needs it, not after.
Sub-agent architectures “Rather than one agent attempting to maintain state across an entire project, specialized sub-agents can handle focused tasks with clean context windows,” reporting back a synthesis, not their scratch work Coordination overhead, and a second window to manage per sub-agent. Anthropic's own research system pairs this with “deterministic safeguards like retry logic and regular checkpoints” because a lead agent juggling several sub-agents is a new failure surface, not a free lunch.
Just-in-time retrieval Keep “lightweight identifiers” in context and fetch the full record only when a tool call actually needs it, instead of pre-loading everything up front Latency — “runtime exploration is slower than retrieving pre-computed data.” You're trading window space for round trips.
These aren't a menu you pick one from

A long-running coding agent plausibly uses all four: notes for decisions made hours ago, compaction when a session nears its limit, sub-agents for isolated investigations, and just-in-time retrieval so the whole codebase is never in context at once. The skill is not memorising the list — it's recognising, for a given symptom, which one actually answers it.

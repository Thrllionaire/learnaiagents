Multi-Agent: What the Extra Agents Cost

Lesson 02's orchestrator–workers pattern was a workflow: you fixed the fan-out-and-merge shape, the model only filled in the subtasks. Today the model picks the shape too — how many workers, on what, and when to stop. That single change is why the same-looking diagram gets a different name, and why the bill looks nothing alike. Three things that look alike and aren't

You've now met three ways one agent hands work to another, and the vocabulary matters because they cost and fail differently.

PatternWho decides the shapeWhere you met it
Orchestrator–workers (workflow) You fix the fan-out and the merge; the model fills in the subtasks Lesson 02
Sub-agent architecture The model decides when to delegate one messy sub-task, for a clean context window Lesson 05
Multi-agent system The model decides how many workers, what each one does, and when it has enough — every run Today

Anthropic's own production research system is the third kind: “a lead agent coordinates the process while delegating to specialized subagents that operate in parallel.” Each subagent is a full agent loop — its own context window, its own tools, its own turns — and the lead is a full agent loop too, except its only “tool” is spawning more agents. Nest the pattern from Lesson 01 inside itself and you have today's build.

The number, again, this time squared

Lesson 02 gave you the first bill: input tokens grow roughly with the square of a single run's length, because the whole transcript is resent every turn. Multi-agent adds a second axis. Every worker is a full agent, paying that same tax independently, and the lead pays it too, on top of whatever the workers report back.

Anthropic's own numbers

“Agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats.”

Chat → agent was roughly 4×, from depth: one run, many turns, resending the transcript each time. Chat → multi-agent is roughly 15× — not 4×4, but the same idea from a second direction: width, several full agent runs happening at once, each paying its own depth tax, then a lead that has to read and merge what came back.

What breaks when agents coordinate agents

The failure modes aren't new categories — they're the workflow-vs-agent argument from Lesson 02, showing up one level up.

FailureWhat it looks like
Duplicated work A vague objective like “research the semiconductor shortage” gives two workers no way to know they're covering the same ground. Both report back, the lead has to notice the overlap itself, and you paid for the duplicate run either way.
No effort scaling Anthropic names this directly: “spawning 50 subagents for simple queries”. A lead with no guidance on how many workers a question deserves treats every question like the hardest one it's ever seen.
Compounding errors, one level up Lesson 02's “95% per step, 60% over ten steps” math still applies inside each worker. Now the lead also has to synthesize from reports it can't fully verify, so a wrong worker report becomes context the lead trusts, the same way a wrong tool result becomes context a single agent trusts.

The delegation instruction is a tool schema you write at runtime

You already know how to fix this — it's Lesson 03 again, one level up. A tool schema is the model's entire view of what a tool does; a bad description sends the model down the wrong path with nothing to correct it. A delegation instruction is the same object: it's the lead's entire view of what a worker should do, and the worker has no other source of truth. Anthropic's fix reads like a tool-description checklist:

“Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries… Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information.” — Anthropic

Today's build hands you a lead whose delegation instruction is one clause long: “Delegate some research to a worker agent.” No objective, no output format, no tool guidance, no boundary. You'll watch what that costs, rewrite it, and watch again.

Evaluating a system you can't fully read

You can't eyeball a multi-agent transcript the way you eyeballed Lesson 08's four-line tool call. There's a lead transcript and N worker transcripts, and the thing you actually care about — did the final answer cover the ground it needed to, accurately — lives in the merge, not in any one piece. Anthropic's own practice reuses everything from Lessons 08–09, at a slightly different scale:

  • Start absurdly small. “Start testing with a small set—about 20 queries representative of real usage patterns” before building anything larger. That's Lesson 09's calibration set, not a validation set, and the same caveat applies.
  • Grade the end state, not the path. Two leads can reach the same correct answer by spawning a different number of workers, in a different order. Grading whether it spawned “the right” workers punishes valid alternate paths; grading whether the final answer is correct doesn't.
  • An LLM judge, plus a human who reads transcripts anyway. The judge scores factual accuracy, citation accuracy, completeness, source quality, tool efficiency — a rubric, same shape as Lesson 09's binary-verdict judge, just with more properties because there's more to check. But “people testing agents find edge cases that evals miss”: hallucinated facts, systematic source bias, the kind of thing that doesn't fail a rubric but is still wrong.
The domain has to earn the pattern

Anthropic is direct about the ceiling: “most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time.” The domains where multi-agent earns its 15× are high-value, genuinely parallel, and produce more information than one context window could hold. A task that's none of those three things should stay a single agent, or a workflow, or one call — the Lesson 02 ladder didn't stop applying just because the pattern got a fancier name.

The lead, not you, decides the topology — how many workers, what each does, when to stop — every run. A delegation instruction needs an objective, an output format, tool/source guidance, and a task boundary; without them workers duplicate work or leave gaps. Your task, about 30 minutes

Everything is in practice/10-multi-agent/. single_agent.py is the baseline you built the measuring habit for in Lesson 02. multi_agent.py is a lead with a spawn_worker tool, shipping with the vague, one-clause delegation instruction the audit above was about. NOTES.md has the checklist. Same house rule as Lessons 08–09: every answer is a sentence you wrote, paste the output before you write it.

  1. Predict. Guess the worker count and the token ratio before running anything.
  2. Baseline. Run single_agent.py. Paste the numbers.
  3. The lead, as shipped. Run multi_agent.py. Read the worker log for overlap. Compute the real token ratio against your baseline.
  4. Fix the delegation instruction. Rewrite SPAWN_WORKER_SCHEMA's description using the four things it needs. Predict what changes, then rerun.
  5. Say no, defensibly. Argue against shipping multi-agent for this exact task, using the three-part “suitable domain” test. Name the one thing that would change your mind.
  6. The sentence. Why should this ship over the single agent — or why shouldn't it? Your numbers, plus one honest caveat about what a 3-item comparison does and doesn't prove.

When the Tool Fails

An error message is the only instruction your harness gets to give a confused agent, and it arrives with a retry budget of about three. Most harnesses spend it on a Python traceback.

A failure is not an exception. It is a turn.

The mechanic is worth stating precisely, because it is what makes error text consequential. A failed tool call does not unwind anything. It comes back as an ordinary tool_result block carrying an extra flag:

{
  "type": "tool_result",
  "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
  "content": "ConnectionError: the weather service API is not available (HTTP 500)",
  "is_error": true
}

That is the documented shape, verbatim from the tool-use docs, and is_error is optional — a flag on a result, not a channel of its own. The loop turns again, the model reads your string alongside everything else in context, and decides what to do next. The model is the recovery mechanism. Your error message is the instruction it recovers by.

The budget you are spending

The docs are specific about what happens next: “If a tool request is invalid or missing parameters, Claude will retry 2-3 times with corrections before apologizing to the user.” That is your whole allowance. Three attempts, each one costing a full round trip, each one steered only by the sentence you wrote. A traceback buys three identical retries and then an apology.

Handled well, this is not damage control — it is the thing agents are unusually good at. From Anthropic's write-up of their production research system: “letting the agent know when a tool is failing and letting it adapt works surprisingly well.” The same post names the other half of the pair, which you will meet in the drill below: they combine that adaptability with “deterministic safeguards like retry logic and regular checkpoints.” Some failures are the model's to handle. Some are yours, and should never reach it.

Why a traceback is the worst available choice

Anthropic's guidance is a single sentence and it is the whole of this lesson's advice: “If a tool call raises an error (for example, during input validation), you can prompt-engineer your error responses to clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks.” Three reasons it matters more than it sounds:

  • It is not actionable. '>' not supported between instances of 'NoneType' and 'int' describes a line of code the model has never seen. It names no input, no constraint, and no alternative. The model's best available move is to try the identical call again.
  • It is expensive and low-signal. A full traceback is a hundred tokens of file paths and frame lines, and it stays in the transcript for every remaining turn of the run — the Lesson 02 arithmetic applies to your failures too.
  • It puts your internals in a context window. Table names, file paths, and library versions become part of a document the model may later summarise or quote. The same docs warn that tool results are the untrusted-content boundary and are where indirect prompt injection lands; filling that channel with your stack trace is the wrong direction of travel. Lesson 07 picks this up properly.

Five failures, five different jobs

“Write better error messages” is not yet advice. The useful question is whose problem is this, because the answer decides which layer handles it — and only one of the five rows below is answered by writing a nicer string.

What happenedWhose problemWhat the result must do
The model called it wrong — bad value, missing argument, wrong format The model's State the constraint, quote back what it sent, and show one valid call. It has two or three tries to use this.
The call was fine; the answer is emptyno late orders Nobody's Not an error. Return a normal result that says so in words. Flagging it teaches the agent its tool is broken, and it will retry a call that worked.
Transient outage — HTTP 503, connection reset, rate limit Yours, for now Retry inside the tool, with backoff. The model should not spend a turn on something your for loop can fix for free.
Persistent outage — still failing after your retries Shared Say what is unavailable, whether waiting helps, and what else could answer the question. "Rate limit exceeded. Retry after 60 seconds."
Your bug — missing config, KeyError, a contract you broke Yours Raise. End the run and tell the human. No wording makes an impossible call succeed, so a retry budget spent here is pure cost.
The cheapest error is the one you made unwritable

Before writing a message for row one, ask whether the failure should exist. Matching c["full_name"].lower() == name.lower() deletes the "priya raman" case entirely. At the schema level, strict tool use (strict: true) goes further: the docs say it “guarantees that tool inputs will always match your schema exactly, preventing missing parameters and type mismatches.” Same move you have made twice now — prefer the fix that makes the bug structurally impossible over the fix that handles it well.

Write it from memory
Reveal once you have written something
  1. Bad input from the model → result with is_error, saying what valid looks like.
  2. Empty answer → ordinary result, in words. Not an error.
  3. Transient outage → retry inside the tool; the model never hears about it.
  4. Persistent outage → result with is_error, naming what is down and what remains possible.
  5. Your own bug → raise, end the run, tell the human.

And the empty set: is_error means the tool did not work. The tool worked. The model spends two or three retries on a call that already succeeded, then apologises to the user for a lookup that was correct the first time. An empty set is an answer.

The trap in step 3

The fastest null guard is if o["shipped_at_epoch_ms"] is None: continue. It stops the traceback and it is wrong — it makes the agent say Marcus has no late deliveries, which is worse than a crash because nobody will notice. If you catch yourself reaching for it, that is the lesson.

Memory: Within-Session vs. Cross-Session State

Lesson 05 kept one conversation's window small. This lesson asks a different question: when the process itself exits — crashes, finishes, gets Ctrl-C'd — what's left? The answer is usually “nothing,” and that's the gap this lesson closes.

Two kinds of state, one easy conflation

Every agent you've built so far has had exactly one place state lives: the messages list. It's a Python list, sitting in RAM, for as long as your script's process is running. That's within-session state — and everything Lesson 05 taught you (compaction, trimming, curating what's in the window) operates entirely inside it.

The conflation to watch for

“I handled context growth” and “my agent remembers things between runs” sound like the same accomplishment. They are not related at all. A flawlessly compacted 40-turn run and a completely uncompacted one both vanish, in full, the instant the process exits — unless something, somewhere, wrote a fact to a file. Compaction is about the window's size. This lesson is about the process's mortality.

Giving it a body: the memory tool

Anthropic's context engineering guidance names the concrete implementation directly: a memory tool that “lets Claude store and retrieve information across conversations in a directory of memory files.” The docs are explicit about what kind of thing it is:

“The memory tool operates client-side: Claude requests file operations, and your application executes them. You control where and how the data is stored through your own infrastructure.” — Memory tool

Read that against what you already know from Lessons 03 and 04: this is not a new kind of thing. It's an ordinary [tool]/[harness] split — the model requests, your code executes, you return a tool_result — applied to file operations instead of a database lookup. Enabling it is one line:

tools=[{"type": "memory_20250818", "name": "memory"}]

That's the entire configuration — no input schema to write, because it's an Anthropic-provided tool. What you owe in return is a handler for six commands, each mapped onto a path under /memories:

CommandDoesSuccess returns
viewDirectory listing, or a file's contents with 1-indexed, tab-separated line numbersThe listing or the numbered content
createWrites a new file"File created successfully at: {path}"
str_replaceReplaces one occurrence of exact text in a file"The memory file has been edited."
insertInserts a line at a given line number"The file {path} has been edited."
deleteRemoves a file (or a directory, recursively)"Successfully deleted {path}"
renameMoves or renames a file"Successfully renamed {old_path} to {new_path}"

Notice what the API does not do: it does not give you storage. “Memory lives entirely in your application,” which is a real files-on-disk directory in today's build task, and could be a database or cloud storage in production. The model only ever emits {"command": "view", "path": "/memories"}; your handler decides what that means.

The API even tells the model to check first

When the memory tool is present, the API automatically injects an instruction you never wrote: “ALWAYS VIEW YOUR MEMORY DIRECTORY BEFORE DOING ANYTHING ELSE” — followed by “ASSUME INTERRUPTION: Your context window might be reset at any moment.” That second line is the mindset this lesson is teaching, stated as a system prompt: treat the in-memory window as disposable, and the files as the only thing that survives.

Not a replacement for compaction — a different axis

Lesson 05's four techniques and this lesson's memory tool are not competing solutions to the same problem. The docs pair them explicitly:

“For long-running agents, consider using both: compaction keeps the active context small without client-side bookkeeping, and memory preserves the information that must survive summarization.” — Memory tool: Using with compaction

One axis is how big is the window right now (Lesson 05). The other is what happens when this process is gone (today). A long-running coding agent needs both: memory files that outlive any single session, and compaction so a single long session doesn't blow its window before it gets the chance to write anything down.

Spot the flaws

Here's a first-pass handler for three of the six commands. It runs — it will pass a quick demo — and it has three real, separately-fixable problems. Find them before you write your own.

AuditFind the three real flaws.

class MemoryHandler:
    def __init__(self, root="./memories"):
        self.root = root

    def view(self, path):
        real_path = self.root + path.replace("/memories", "")
        with open(real_path) as f:
            return f.read()

    def create(self, path, file_text):
        real_path = self.root + path.replace("/memories", "")
        with open(real_path, "w") as f:
            f.write(file_text)
        return f"File created successfully at: {path}"

    def str_replace(self, path, old_str, new_str=""):
        real_path = self.root + path.replace("/memories", "")
        with open(real_path) as f:
            content = f.read()
        content = content.replace(old_str, new_str)
        with open(real_path, "w") as f:
            f.write(content)
        return "The memory file has been edited."

    def delete(self, path):
        real_path = self.root + path.replace("/memories", "")
        os.remove(real_path)
        return f"Successfully deleted {path}"

Reveal once you have written something

A memory file survives the process exiting; messages is RAM and dies with it. The traversal bug: stripping a string prefix ("/memories") and trusting the remainder lets .. segments walk the real filesystem path outside the memory root — the fix is resolving to a canonical absolute path and checking containment, not string substitution.

Your task, about 20 minutes

Everything is in practice/06-memory/. Run it as two separate process invocations, not one script called twice — that's the whole point:

uv run python practice/06-memory/memory_agent.py "<prompt>"
  1. Implement MemoryHandler. Five TODOs: _resolve (map /memories/... onto a real path and refuse anything that resolves outside the root), view, create, str_replace (exactly one occurrence, or an error), and delete (refusing the root itself).
  2. Session one. Run with a prompt telling it to remember a preference and save it. Record what it called, in order, and what landed in practice/06-memory/memories/.

  5. One line, out loud. The property a memory file has that messages never had — and the property messages has that a memory file doesn't.

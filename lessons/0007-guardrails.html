One refusal is not a policy

Nothing about last lesson's refusal was fake. Claude really did decline. The problem is what that refusal ran on: a plainly-worded, clearly hostile-sounding request, typed by a person, in the same turn the model was already reasoning about. That is close to the best case for a model's own training-shaped judgment to catch something.

A prompt-injected instruction rarely looks like that. It arrives inside a tool_result — the contents of a file the model asked to view, a scraped web page, another tool's output — dressed as ordinary data, not as a request from anyone. The Claude docs warn about this directly: content coming back through a tool_result should be treated the same way you'd treat any other untrusted input, because nothing guarantees the model's refusal reflex fires the same way on data as it does on a direct ask.

Four layers, not one

Anthropic's Trustworthy agents in practice names the shape of the problem directly: safety isn't one property of the model, it's a property of four separate layers — the model, a harness, tools, and an environment — and “no single line of defense is enough to guarantee protection,” which is why “the safeguards we and others build need to account for them all.”

The conflation to watch for

“The model generally does the right thing” is a statement about the model layer. It is not a substitute for anything at the harness layer, no matter how reliably it seems to hold in testing — because the one time it's tested against a plain, typed-out, obviously-suspicious request is not the case a real attacker sends.

The harness's job: a gate before every call

The mechanism is specific: something that intercepts every tool_use block before it reaches execution, and decides allow, ask, or deny from the actual command and its actual arguments — not from whether the model sounded confident, and not from what the model claims it's trying to do.

This isn't hypothetical machinery invented for this lesson. It's what the tool you're reading this lesson through already does to itself. Claude Code's own permission system gates every tool call through allow/ask/deny tiers by default, and its auto mode replaces the human at the "ask" tier with a classifier that inspects the actual pending action. One detail is worth sitting with:

“We strip assistant text so the agent can't talk the classifier into making a bad call.” — How we built Claude Code auto mode

The classifier doesn't see the model's justification for the action — only the action itself. A model that has been talked into something bad by an injected instruction is, by definition, going to produce a reasonable-sounding justification for it. A gate that reads that justification is grading the model's own essay about why it should be trusted. A gate that only ever sees the command and its arguments can't be argued with.

Spot the flaws

Here's a first pass at a gate. It runs, it does stop something, and it has three real, separately-fixable problems.

AuditFind the three real flaws.

DANGEROUS = {"delete"}

def guarded_execute(memory, command, **kwargs):
    if command in DANGEROUS:
        print(f"About to run {command} on {kwargs.get('path')}")
        reply = client.messages.create(
            model=MODEL,
            max_tokens=100,
            messages=[{"role": "user", "content":
                f"Is it safe to {command} {kwargs.get('path')}? Answer yes or no."}],
        )
        if "yes" not in reply.content[0].text.lower():
            return "Error: denied by safety check"
    return memory.execute(command, **kwargs)

Write it from memory
Reveal once you have written something

A harness gate's decision doesn't depend on the model's cooperation at all — it runs on the actual command and arguments, in code the model never touches, so nothing the model was talked into can talk the gate out of enforcing its policy. And a gate that can be routed around by a second call site to the same function isn't a boundary; it's only a boundary if every path to execution goes through it, which is why today's build task wires the gate directly into the loop rather than leaving memory.execute reachable on its own.

Build it

Your task, about 20–25 minutes

Everything is in practice/07-guardrails/. MemoryHandler is Lesson 06's working version, given as-is — today's work is all in PermissionGate and in run():

uv run python practice/07-guardrails/guardrail_agent.py "<prompt>"
  1. Implement PermissionGate.check. "allow" commands proceed immediately. "ask" commands print the actual command and path, then require an explicit "y" at a real terminal prompt — anything else denies. Anything not in POLICY at all denies by default.
  2. Wire the gate into the loop. Every tool_use block must go through gate.check before memory.execute runs. A denial means memory.execute is never called — the tool_result reports the denial instead.
  3. Confirm a real delete gets stopped. Write a scratch file, then in a fresh invocation ask it to delete that file and answer n at the prompt. Confirm the file survives.
  4. The prompt injection test. Seed a memory file on disk (not through the agent) containing an embedded instruction telling the model to delete /memories. Ask an innocuous question that makes the model view that file. Record, from the actual transcript — not a guess — whether the model attempted the injected call, and if it did, what actually stopped it.
  5. One line, out loud. What PermissionGate has that “the model generally refuses unsafe requests” doesn't.

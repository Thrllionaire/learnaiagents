Evals: One Run Is an Anecdote

Lessons 06 and 07 both ended the same way. You ran a test once, looked at what happened, and wrote down a verdict. The verdicts were mostly right, but each one was a single sample from a model that doesn't give the same answer twice. This lesson swaps the verdict for a number: several trials, graded by code, from a harness that keeps every transcript so you can read what the number is made of.

The vocabulary

Anthropic's Demystifying evals for AI agents uses a small, precise vocabulary. It's worth adopting as-is, because each word names a separate part of the harness you're about to use:

TermDefinition (quoted)In today's harness
Task “A single test with defined inputs and success criteria.” Task: a prompt, seeded files, graders
Trial “Each attempt at a task”, and “because model outputs vary between runs, we run multiple trials.” run_trial(), --trials K
Transcript “The complete record of a trial, including outputs, tool calls, reasoning…” Trial.log, saved to runs/*.json
Outcome “The final state in the environment at the end of the trial.” What's on disk in Trial.root
Grader “Logic that scores some aspect of the agent's performance.” Your four TODO functions

Measured against that table, Lesson 07's injection test was one task, one trial, and a grader that was you reading the terminal. There's nothing wrong with any of those parts. There just wasn't enough of any of them to support a claim like “the agent resists injection.”

Look before you grade

The natural instinct is to write assertions first. Hamel Husain's Your AI Product Needs Evals says to do the reverse: read what the system actually did, and let the assertions come from what you saw. “If you have trouble thinking of assertions, you should critically examine your traces and failure modes.” He also says “You must remove all friction from the process of looking at data.”

That's why today's harness writes every trial's transcript to a JSON file, and why the first build step runs with --no-grade. The graders you write should come from behaviour you've read, not behaviour you assumed. The same transcripts are also how you later check the graders themselves:

“You won't know if your graders are working well unless you read the transcripts and grades from many trials.” — Demystifying evals for AI agents

Two graders, two layers

Every injection task in today's harness has two code-based graders, and they're kept apart on purpose:

GraderLooks atQuestion it answers
files_surviveOutcome: the disk Did anything actually get destroyed?
no_delete_requestedTranscript: tool calls Did the model try?

Anthropic's default advice is to prefer the first kind: “it's often better to grade what the agent produced, not the path it took,” because checks on the path break whenever the model finds a different valid route. The same post also lists “tool calls verification (tools used, parameters)” as a legitimate code-based grader. It's the right choice when the call itself is the behaviour you're measuring, and here it is.

Now apply Lesson 07. With the gate on, and the scripted human answering n, can files_survive ever fail on an injection task?

The mislabelled metric

It can't. The gate blocks the delete whatever the model does, so files_survive reads 5/5 on a model that falls for the injection every time. If you report that number as “injection resistance”, you're making Recall 2's mistake again: a real number under the wrong label. With the gate on, the outcome grader measures the gate and the transcript grader measures the model. Build step 4 checks this by removing the gate.

One more thing the task list does on purpose. It includes legit-delete, a task where deleting is correct. Without it, an agent that never deletes anything would score perfectly on every injection task. “Test both the cases where a behavior should occur and where it shouldn't. One-sided evals create one-sided optimization.” (Anthropic)

Which grader?

One trial is not a rate

Once you have several trials, two numbers matter, and they answer opposite questions (Anthropic):

  • pass@k: “the likelihood that an agent gets at least one correct solution in k attempts.” That's the right number when you can retry and keep the best result.
  • pass^k: “the probability that all k trials succeed.” That's the right number when every attempt counts, and a guardrail is exactly that case. An attacker needs only one success.

The worked example from the same post: “If your agent has a 75% per-trial success rate and you run 3 trials, the probability of passing all three is (0.75)³ ≈ 42%.” A number that sounds reassuring per trial falls apart once it's repeated.

CheckYour no_delete_requested grader passes on 90% of inj-polite trials. The agent will read that poisoned note five times this week. What's the chance it resists every time?

One sanity rule from the same source, for when a number looks too bad: “With frontier models, a 0% pass rate across many trials… is most often a signal of a broken task, not an incapable agent.” Suspect the grader before you suspect the model. The same applies in reverse. A grader you've only ever seen pass hasn't been tested yet, which is Lesson 07's frobnicate bug again, and why the build includes a selftest().

Build it

Your task, about 20–25 minutes

Everything is in practice/08-evals/. The harness imports MemoryHandler and your PermissionGate directly from practice/07-guardrails/, so it measures your code. NOTES.md has the checklist, and one house rule: every answer is pasted output first, then your read of it.

  1. Look first. --no-grade --trials 3, then read every transcript in runs/gate/. Write one line per task on what the model actually did.
  2. Write the graders. file_gone, no_delete_requested, delete_requested. Each is two or three lines; files_survive is the worked example.
  3. Prove they can fail. Implement selftest(): hand-built bad and good Trials, no model calls. Run --selftest.
  4. Run it, then remove the gate. Predict which grader's numbers will move under --no-gate before running it. Paste both tables.
  5. One line. The pass^5 for inj-polite from your real numbers, and what you'd say to a teammate who reports “I ran the injection test and it passed.”

This is 20 trials on Haiku, which costs cents. Don't cut the trial count to save money: the trial count is the point of the lesson.

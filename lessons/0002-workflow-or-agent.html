The spectrum, and the one question

"Agent" is a marketing word and a technical word, and the gap between them is where careers get made. Anthropic's definition is the one the field actually uses, and it is narrow: "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents … are systems where LLMs dynamically direct their own processes and tool usage."

Notice what does not appear in that definition: the number of LLM calls, the presence of tools, or how clever the system looks. A five-call, three-tool, RAG-backed pipeline is a workflow if you drew the arrows. A two-call system is an agent if the model chose the second call. The distinguishing variable is who owns the control flow — and you already proved this to yourself in Lesson 01, where the run ended because the model set stop_reason, not because your code counted to two.

So the decision collapses to one question, asked before you see any input:

The question

Can you draw the flowchart in advance?

If yes, and it is one box, you want a single call. If yes, and it is several boxes, you want a workflow. If you genuinely cannot draw it — because the steps depend on what earlier steps discover — that is the case an agent exists for, and the only one.

Question 1 is the one people skip, and it is the one that saves the most money. Anthropic's guidance opens with it: "find the simplest solution possible, and only increase complexity when needed. This might mean not building agentic systems at all."

The five workflow shapes

If you land on "workflow", you are not inventing an architecture. There are five shapes in common use, and they cover nearly everything. Learn them as a vocabulary: naming the pattern you are proposing is most of what makes a design review go well.

PatternShapeUse when
Prompt chaining Call → call → call, output of one feeding the next The task splits cleanly into fixed subtasks. You are trading latency for accuracy
Routing Classify, then branch to one of N specialised paths Distinct categories are better handled separately, and classification is reliable
Parallelization
sectioning & voting		 Run N calls at once, then aggregate. Sectioning: different subtasks. Voting: same task, several attempts Subtasks are independent (speed), or you need several perspectives on one thing (confidence)
Orchestrator–workers One call decides the subtasks, spawns workers, merges results You cannot predict which subtasks are needed, but you can predict the merge
Evaluator–optimizer Generate, critique, regenerate, until the critic passes it You have clear evaluation criteria and iterative refinement measurably helps
Where the line genuinely blurs

Orchestrator–workers and evaluator–optimizer both hand the model a real decision, and people argue about whether they are workflows at all. The useful distinction is scope: in both patterns you fixed the shape of the graph — a fan-out and a merge, a generate-critique cycle — and the model only fills in the contents. In an agent, the model picks the shape too. If someone challenges you on this in an interview, that is the answer: the boundary is whether the topology is yours.

What agency actually costs

Every one of these is cheaper than an agent, and the gap is not small. The reason the ladder is biased downward is that agency is a purchase, and it is worth being able to itemise the bill.

You pay inBecause
Tokens The transcript is re-sent every iteration. Input cost grows roughly with the square of the run length — the thing you just recalled
Latency Iterations are strictly sequential: the model cannot choose step 4 until it has seen the result of step 3. A workflow's independent branches can run at once
Determinism The same input can take a different path on Tuesday. You cannot write a unit test for a path you did not choose
Error compounding A wrong step becomes context for the next step. Per-step accuracy of 95% over ten steps is about 60% end-to-end, and the run still looks plausible
Blast radius An agent that can act for many turns needs, in Anthropic's words, "some level of trust in its decision-making" — and therefore sandboxing, gating, and review that a workflow does not
The failure you have already seen

In Lesson 01 your agent ran with a missing schema and returned a confident, well-formed, partly-unfounded answer. Nothing crashed. That is the normal failure mode of an agentic system, and it is what "compounding errors" feels like from the outside: not a stack trace, but a plausible paragraph.

A workflow fails differently. When step 3 of a fixed chain breaks, you know it was step 3. That debuggability is a real, costed feature, and it is a legitimate reason to choose a workflow even when an agent would work.

None of this says don't build agents. It says the burden of proof sits on the agent. Agents earn their cost on "open-ended problems where it's difficult or impossible to predict the required number of steps, and where you can't hardcode a fixed path." When that is true, a workflow cannot do the job at any price, and the argument is over.

Saying no, defensibly

You will usually be arguing against an agent, often with someone senior who has already told a customer the word. Three moves make that argument land.

  1. Concede the capability, contest the fit. Never "an agent can't do that." Always "an agent can do that, and here is what it costs us versus the version that can be tested." You are having a budget conversation, not a capability one.
  2. Quantify one axis. Pick the cheapest number to produce — usually tokens or latency — and measure it on the real task. "The agent version is 7× the tokens and 4× the p95" ends an argument that an opinion cannot. You will produce exactly this number in the build task below.
  3. Name the trigger that would change your mind. This is the move that separates a seasoned engineer from a contrarian. "Ship the router; if the fallback bucket exceeds 15% of tickets, that is the signal that the categories don't cover reality and we escalate to an agent." You have now proposed an experiment rather than won a debate.
The sentence worth memorising

"Success in the LLM space isn't about building the most sophisticated system. It's about building the right system for your needs."

It sounds like a platitude until you have watched a team spend a quarter on an agent that a routing workflow would have beaten on accuracy, cost, and ship date.

Build it

Time to produce the number from move 2. You will implement the same task twice and measure the difference, which turns "agents are expensive" from something you read into something you have on your own terminal.

Your task, about 12 minutes

Work in practice/02-workflow-vs-agent/. Run everything with uv run python ....

  1. Copy your Lesson 01 agent to agent_measured.py. Inside the loop, after each response, accumulate response.usage.input_tokens and response.usage.output_tokens, and count the API calls. Print all three totals at the end.
  2. Write workflow.py: the same question — weather and time in Tokyo — with no loop and no tools=. You call get_weather("Tokyo") and get_time("Asia/Tokyo") yourself, in Python, then make one messages.create call that includes both results in the prompt and asks for the answer. Print the same three totals.
  3. Compare. Write both sets of numbers into NOTES.md. How many times more input tokens did the agent spend to reach the same sentence?
  4. Now find the input that breaks the workflow. Think of a question your hardcoded version answers wrongly or not at all, but the agent handles. Run it against both. Write down what each did.
  5. Finish with one paragraph in NOTES.md: given those numbers and that broken input, which would you ship, and what would have to change for you to switch? This is the interview answer, and writing it down is the exercise.

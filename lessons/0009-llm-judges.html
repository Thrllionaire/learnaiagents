LLM Judges: Measure the Grader

In Lesson 08's transcripts, the agent told the user “I'll delete the notes file as requested.” Nobody had requested it. The instruction came from a note inside the file. None of your four graders could see that, because it isn't a file state or a tool call. It's a claim in the reply, and whether that claim is true is a question about meaning. Today a model grades that question. Before you trust its answers, you'll measure how often it agrees with yours.

What code can't grade

Try writing that as a regex. If you match "as requested", you fail gate/3, which does say where the instruction came from. You also miss any silent delete that doesn't happen to use the phrase. What you're grading is honesty of the report, and that sits in what the words mean, not in which words appear. Anthropic's list of model-based grader methods starts with “rubric-based scoring” and “natural language assertions”. Its list of their costs ends with the one this lesson is about: “Requires calibration with human graders for accuracy” (Demystifying evals).

Label before you prompt

The obvious order is: write a judge prompt, run it, glance at the output. The research says to do it the other way round. Shankar et al. watched experts grade LLM outputs and named what they saw:

“users need criteria to grade outputs, but grading outputs helps users define criteria.” … “it is impossible to completely determine evaluation criteria prior to human judging of LLM outputs.” — Who Validates the Validators? (criteria drift)

You'll run into this within five cases. Is gate/3 a pass because it names the note as the source? Is nogate/3 a pass because it says it will delete, even though it never confirms the delete happened? You don't have a rule for either until you meet the case. Your labels are the spec, and the judge prompt is written from them. If you write the prompt first, it tends to shape the labels, and then you end up measuring the prompt against itself.

Hamel Husain's version of this, which he calls critique shadowing, has two rules that today's labels.json enforces (Using LLM-as-a-Judge):

  • Binary. “Just a clear pass or fail decision.” “If your evaluations consist of a bunch of metrics that LLMs score on a 1-5 scale… you're doing it wrong.” The evals FAQ gives the reason: the gap between a 3 and a 4 “is subjective and inconsistent across annotators,” and annotators “default to middle values to avoid making hard decisions.”
  • A critique with every verdict. It should be “detailed enough that a new employee could understand it. Being too terse is a common mistake.” The critique is what you check the judge's reasoning against. It's also the raw material for the prompt.

The number that says whether to trust it

Your labels are the ground truth. The obvious measure is raw agreement: the fraction of cases where the judge's verdict matches yours. Hamel's guide reports exactly that, and then adds a warning:

“we used agreement… because our dataset was roughly balanced (about 50% of instances were failures). Raw agreement can be misleading when classes are imbalanced. Treat the human labels as ground truth and report the judge's True Positive Rate and True Negative Rate separately.” — Husain

With “positive” meaning a failure is present (FAQ definitions):

  • TPR: of the cases you failed, the fraction the judge also failed. The failures it catches.
  • TNR: of the cases you passed, the fraction the judge also passed. The good outputs it leaves alone. Everything else is a false alarm.

CheckThis example is made up for illustration. In production, 10 of 200 agent replies are dishonest reports. A judge that returns “pass” for every reply scores what?

Eugene Yan makes the same point from another direction. Percent agreement “doesn't account for agreement due to random chance,” and one judge he cites had 80% agreement but a Cohen's κ of only 0.62 (Yan). Kappa is one number that corrects for chance. TPR and TNR are two numbers that show which way the judge is wrong, and that's what you need to decide what to fix.

Twenty labels is a calibration, not a validation

Hamel: “Validating an automated judge needs a larger labeled set. Aim for about 100 examples per failure mode… Below 60 examples, the confidence intervals are often too wide to support a useful conclusion.” Today's 20 are enough to find out where the judge and you disagree, and why. They aren't enough to claim a TPR to the percent. A second trap: if you tune the prompt on the same 20 cases you report on, you're overfitting. “It may do well on the dev set but poorly on new examples” (FAQ). The fix is a held-out test set you only look at at the end. Both caveats belong in step 5's sentence.

Criteria drift: you don't know your own criteria until you've graded real outputs, and grading changes them. Labels written first are the spec, and the prompt is written from them. A prompt written first tends to shape the labels, and then the measurement is circular. Raw agreement rewards a judge for how rare failures are. An always-pass judge scores high agreement while catching nothing. TPR says how many real failures it catches, and TNR says how many good outputs it wrongly flags. They trade off against each other, and which one matters more depends on what a missed failure costs.

Build it

Your task, about 25 minutes

Everything is in practice/09-llm-judge/. The cases are 20 of your own Lesson 08 transcripts, read from disk, so no agent calls are made. NOTES.md has the checklist. One new house rule: every answer is a sentence you wrote.

  1. Step 0. Paste the teammate sentence you wrote above.
  2. Label. Run --show and read all 20. Fill in labels.json with a verdict and a critique for each. Note every time you changed an earlier call: that's criteria drift, happening to you.
  3. Baseline. Implement agreement() and run --always-pass. No API calls.
  4. Judge. Write JUDGE_PROMPT from your critiques. Predict the disagreements, then run it.
  5. Read every disagreement. Decide who was wrong and fix that side, prompt or label. Run v2.
  6. The sentence. “Why should I trust this judge?” Answer with TPR, TNR, n, and one caveat.

Twenty Sonnet calls per run, so a few cents. Changing a label is allowed. What isn't allowed is changing a label to match the judge when you still believe the label was right.

Which pattern you're actually building, what it costs, and the checklist for the one instruction the whole system depends on.

Which pattern is it

PatternWho fixes the topology
Orchestrator–workers (workflow) You: the fan-out shape and the merge step are fixed code. The model fills in what the fixed number of subtasks contain.
Sub-agent architecture The model decides when to delegate one sub-task, for a clean context window — not for parallelism.
Multi-agent system The model: how many workers, what each does, when it has enough. Every run can look different. This is an agent, built from workflow-shaped pieces (a fan-out, a merge) nested inside it.

The cost, in order of where it comes from

~4×agent vs. one chat call — depth: the transcript resent every turn of one run.
~15×multi-agent vs. one chat call — width: several full agent runs at once, each paying the depth tax, plus a lead that reads and merges what comes back.

Source: Anthropic, How We Built Our Multi-Agent Research System.

The three-part fit test

All three, or don't build it:

  1. Value high enough to justify ~15× the tokens of a single call.
  2. Real parallelizable work — independent sub-tasks, not a sequence with heavy interdependencies (“most coding tasks involve fewer truly parallelizable tasks than research”).
  3. More information than one context window can hold, or a tool interface too complex for one agent to hold in its head.

The delegation instruction checklist

Every worker's entire view of its job. Missing any of these: duplicated work, gaps, or a worker that can't find what it needs.

ObjectiveWhat, specifically, this worker is finding out — not the whole question restated.
Output formatWhat shape the report back should take, so the lead can merge it without another round trip.
Tool / source guidanceWhich tools to use and how. “Bad tool descriptions can send agents down completely wrong paths.”
Task boundaryWhat this worker owns, so a second worker with a different objective can't end up covering the same ground.

Effort scaling

Give the lead an explicit rule of thumb, or it treats every question like the hardest one it's seen: simple fact lookup → 1 agent, a handful of tool calls. Comparison across a few items → 2–4 subagents. Open-ended research → 10+ subagents with divided responsibilities. Without a rule, expect “spawning 50 subagents for simple queries.”

Evaluating it

  • Start with ~20 realistic queries — a calibration set (see Reference 09), not a validation set.
  • Grade the end state: whether the final answer is correct and complete. Not the path — two correct runs can spawn different numbers of workers in a different order.
  • An LLM judge scores a rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) — one judge, several properties, because there's more surface than a single binary-verdict judge covers.
  • Read transcripts yourself anyway. “People testing agents find edge cases that evals miss”: hallucinations, systematic source bias, things that pass a rubric and are still wrong.

The sentence for a design review

“Multi-agent costs about n× the tokens of a single agent on this task, measured on our own run. It's worth it because [value / parallel work / window size] — and here's the trigger that would make me pull it back to a single agent: …”

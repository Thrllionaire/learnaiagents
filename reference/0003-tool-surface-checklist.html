Tool Surface Checklist

Run this over any tool before it ships. Print it. The five questions are the card; everything below them is the worked detail.

Reference 03· ACI design· Verified 2026-09-20

The five questions

#QuestionFailing looks like
1 Task or endpoint? Does the tool match a step a human would take? One tool per route in your API docs
2 Usable from the description alone by a capable new colleague? "Searches the database and returns results."
3 Every parameter name unambiguous? user where you meant user_id
4 Result high-signal? Meaning over identifiers. A payload of UUIDs and mime_type
5 What happens at ten thousand rows? No default limit, or a silent truncation

1 · Consolidate around the task

"More tools don't always lead to better outcomes." Collapse a sequence a human would perform into one tool.

Endpoint-shapedTask-shaped
list_users + list_events + create_eventschedule_event
read_logssearch_logs
get_customer_by_id + list_transactions + list_notesget_customer_context

The limit of the rule. Consolidation spends flexibility to buy tokens. Split when a human would genuinely want the pieces separately; merge when they would always take them together. Not "fewer tools", but tools shaped like the work.

Namespacing, once several tools could collide: by service (asana_search, jira_search) or by resource (asana_projects_search, asana_users_search). Prefix versus suffix had "non-trivial effects on tool-use evaluations" — worth testing both if the agent is confusing them.

2 · The description is prompt

The model cannot see your code. Name, description, and schema are its entire knowledge of the tool. Write them as onboarding notes for a capable colleague who joined this morning: make implicit context explicit, define niche terminology, and state how resources relate.

# Weak — the model must guess whether this tool applies.
"description": "Searches the database and returns results."

# Strong — scope, contents, matching behaviour, and limits.
"description": (
    "Search support tickets by free-text query across subject and body. "
    "Covers the last 18 months only; older tickets are archived and not "
    "searchable here. Returns the 20 most recent matches by default, "
    "newest first. Use get_customer_context instead when you already "
    "know the customer and want their full history."
)

Anthropic calls prompt-engineering these descriptions "one of the most effective methods for improving tools"; refinements to tool descriptions alone took Claude Sonnet 3.5 to a state-of-the-art SWE-bench Verified result.

3 · Name parameters so only one reading survives

AmbiguousUnambiguousWhat the type could not say
useruser_idid, email, handle, or display name
datedate_from / date_toa bound, or a single day
idorder_idwhich resource it belongs to
limitmax_resultsrows, bytes, or seconds

Describe every parameter, including optional ones, and state the default an omitted parameter produces. Consider strict: true on the tool definition (requires additionalProperties: false plus required) when malformed arguments would be expensive — it guarantees the input validates against your schema exactly.

4 · Return meaning, not identifiers

Low-signal

{"uuid": "7f3c9a1e-...",
 "owner_uuid": "a91f-...",
 "mime_type": "image/png",
 "256px_image_url": "...",
 "status_code": 3}

High-signal

{"name": "Q3 revenue deck",
 "owner": "Priya Raman",
 "file_type": "image",
 "image_url": "...",
 "status": "awaiting review"}

Resolving UUIDs into semantic language "significantly improves Claude's precision in retrieval tasks by reducing hallucinations". Keep identifiers only where a downstream call needs them.

Let the agent choose verbosity. A response_format enum of "concise" / "detailed" lets it pay for identifiers only when it will use them. Anthropic's Slack example: 206 tokens detailed against 72 concise.

Format — XML, JSON, or Markdown — has "no one-size-fits-all solution". Test rather than assume.

5 · Cap the response, and say that you did

Pagination, range selection, filtering, or truncation — with sensible defaults. Claude Code caps tool responses at 25,000 tokens by default.

# Silent: the agent answers confidently from a slice it cannot see is a slice.
return rows[:50]

# Steering: states the limit, then names the cheaper strategy.
return (
    f"Showing 50 of {total} matches, newest first. "
    f"Narrow with date_from/date_to or a more specific query "
    f"rather than requesting the full set."
)

Proving it, in one line

Measure a tool surface the way you measured the agent: on a fixed task, record tool calls, API calls, input tokens, tool errors, and whether the final answer was right. A redesign that halves the tokens and keeps the answer is a result you can put in a design doc. This is the seam where tool design meets evals (Lesson 08): Anthropic builds evaluation tasks that need dozens of tool calls, runs them in a plain while loop, then feeds the transcripts back to Claude to refactor the tools — and reports that the refactored versions beat their own expert hand-written ones on held-out tests.

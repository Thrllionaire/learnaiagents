The four layers

From Trustworthy agents in practice: safety is not a property of the model alone. Four independent layers, each responsible for something the others can't guarantee:

LayerResponsible forFails when…
Model Training-shaped judgment — declining an obviously hostile request The request doesn't look hostile because it arrived as ordinary tool output, not as a direct ask
Harness Code that runs regardless of what the model wants — gating, resolving paths, logging A dangerous call has a second path to execution that skips the gate
Tools Which capabilities exist at all — the narrower the surface, the less damage a mistake anywhere else can do A tool exposes more than the task needs (a broad delete when only "delete one named file" was required)
Environment What's physically reachable from where the process runs The process has filesystem or network access wider than any tool was designed to use
The rule that generalizes

“The model generally refuses unsafe requests” is a fact about the model layer. It is never a substitute for a harness-layer check, because the case that gets tested (a blunt, typed-out request) is not the case that gets attacked (an instruction smuggled inside a tool_result).

Permission gate design

TierMeaningDecided by
allow Runs immediately Policy, keyed on command and its actual arguments — never command name alone
ask Requires an explicit human approval before running A real prompt shown to a person, not a second model call
deny Never runs Policy — and the default for any command not explicitly listed
  • Judge the action, not the justification. Claude Code's auto-mode classifier strips the model's own reasoning before evaluating a pending action: “We strip assistant text so the agent can't talk the classifier into making a bad call.” A gate that reads the model's stated intent is gradable by whatever talked the model into the bad call in the first place.
  • The check must be the only path to execution. If the underlying handler (memory.execute, a database client, a shell call) is reachable from anywhere else in the codebase without going through the gate, the gate is a speed bump, not a boundary.
  • A second model call is still the model layer. Asking Claude “is this safe?” and trusting the answer is not a harness decision — it's the same layer as the thing it's meant to check, run twice.
  • An allowlist is not a sandbox. A whitelist says which tools may be invoked; it says nothing about what those tools can reach once invoked. Claude Code's own permission docs pair its allow/ask/deny tiers with separate sandbox isolation (bubblewrap on Linux, Seatbelt on macOS) for exactly this reason — two different questions, two different mechanisms.
  • Treat every tool_result as untrusted input. Per the Claude docs, content coming back through a tool result can carry an injected instruction and should be handled with the same suspicion as any other external input — regardless of how the model reacts to it in a given run.

Testing a gate: transcript, not verdict

“I asked it to do the bad thing and it didn't” has two different causes, and only one of them is your code: the model declined on its own (nothing exercised), or the model attempted it and the gate stopped it (the thing under test actually ran). Confirm which one happened from the transcript — what the model actually called, in order — not from the final answer alone. When in doubt, force the harness-only path: call the handler directly, bypassing the model, the way Lesson 06's traversal test did.

Error Message Patterns

What a tool says when it cannot do the thing. Five failure classes, where each is handled, and the sentence shape that works. Print it and keep it next to the tool surface card.

The routing table

missing config, KeyError, broken contract		 You Raise. End the run. Page a human. No retry can succeed.
The single most useful fact on this card

"If a tool request is invalid or missing parameters, Claude will retry 2-3 times with corrections before apologizing to the user." Your error string is the only steering those retries get. Budget accordingly.

The sentence shape

Three beats, in order. Anthropic's own worked example fits in six words: "Rate limit exceeded. Retry after 60 seconds."

  1. What happened, in the tool's own vocabulary — quoting the input back where the input is the problem.
  2. Why — the rule or state that made it fail.
  3. What to do instead — a call the model can actually make, or an explicit "waiting will not help".

Beat three is the one that gets dropped, and it is the one that converts a retry into a recovery.

The shape on the wire

{
  "type": "tool_result",
  "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
  "content": "ConnectionError: the weather service API is not available (HTTP 500)",
  "is_error": true
}
  • is_error is optional and defaults to absent. It is a flag on a normal result, not a separate channel.
  • A failed call still needs a tool_result. Dropping it produces "tool_use ids were found without tool_result blocks immediately after".
  • All results for one assistant turn go back in one user message, failures included, with the tool_result blocks first in the content array and any text after them.
  • Server tools (web search, code execution) handle their own errors. You do not return is_error for those.

Three rules worth memorising

  1. An empty set is data, not a failure. is_error on "no rows" spends the retry budget on a call that already worked, and ends in an apology for a correct lookup.
  2. Never let a failure look like an empty answer. "No open tickets" and "the ticket service is down" produce different answers, and only one of them is true. This is silent truncation wearing a different hat.
  3. Prefer the fix that makes the error unwritable. Case-insensitive matching deletes a whole error class; strict tool use (strict: true) "guarantees that tool inputs will always match your schema exactly, preventing missing parameters and type mismatches."

Two things to be careful about

Tracebacks leak. Table names, file paths and library versions end up in a context window that the model may summarise or quote later. Tool results are also the boundary where untrusted content enters — the docs flag them as where indirect prompt injection lands — so keep that channel narrow and yours.

Errors persist. Every failed attempt stays in the transcript and is re-sent on every subsequent turn. A verbose error is not paid for once; it is paid for on every remaining call of the run.

Recovery is a system property, not just a string

Anthropic's production research system pairs the two halves explicitly: "letting the agent know when a tool is failing and letting it adapt works surprisingly well", combined with "deterministic safeguards like retry logic and regular checkpoints." They also note the reason checkpoints matter: "When errors occur, we can't just restart from the beginning: restarts are expensive and frustrating for users." An agent mid-run is stateful; the transcript is the state, and resuming beats restarting.

The definition that settles it

TermDefinitionWho picks the path
Workflow LLMs and tools orchestrated through predefined code paths You, at design time
Agent LLM dynamically directs its own process and tool usage The model, at run time

Call count, tool count, and apparent sophistication are irrelevant to the classification. Only control-flow ownership matters.

The ladder

Ask in order. Stop at the first exit.

#QuestionIf noIf yes
1 Does any step need judgement no rule can express? Plain code. No LLM Go to 2
2 Can you draw the whole path before seeing the input? Agent Go to 3
3 Does that path have more than one LLM step? Single call Workflow — pick a pattern below
Why the order matters

The ladder only reaches "agent" by failing to draw the path. It is never reached by wanting one. Asking "is this agentic?" first inverts the bias and is how teams end up shipping a loop where a match statement belonged.

The five workflow patterns

PatternUse whenExample
Prompt chaining
call → call → call		 Task decomposes cleanly into fixed subtasks. Trading latency for accuracy Write marketing copy, then translate it. Outline, then draft
Routing
classify → branch		 Distinct categories are better handled separately and classification is accurate Support query types to specialised prompts. Easy queries to a cheap model
Parallelization
fan out → aggregate		 Sectioning: independent subtasks, run for speed. Voting: same task N times, run for confidence Sectioning: a guardrail screen alongside the main call. Voting: N reviewers flagging vulnerabilities
Orchestrator–workers
plan → fan out → merge		 You cannot predict which subtasks are needed, but you fixed the fan-out-and-merge topology A code change spanning an unknown set of files. Multi-source search
Evaluator–optimizer
generate ⇄ critique		 Clear evaluation criteria and iterative refinement measurably helps Literary translation with critique rounds. Multi-round search refinement
The boundary case, answered

Orchestrator–workers and evaluator–optimizer both give the model a real decision, and get called agents in casual use. The distinction that holds up: you fixed the topology — a fan-out and a merge, or a generate-critique cycle — and the model only fills in the contents. In an agent the model picks the topology too. If someone presses, that is the answer.

What agency costs

AxisAgentWorkflow
Input tokens Transcript re-sent each iteration → grows ~quadratically with run length Each step pays only for its own prompt
Latency Strictly sequential; step n+1 is unknown until n returns Independent branches parallelize
Determinism Same input may take a different path on a different day Path is fixed; steps are individually testable
Errors Compound — a wrong step becomes context for the next. 95% per step over 10 steps ≈ 60% end-to-end Localised — you know which step failed
Debugging Read a trace, reconstruct a path that will not recur Re-run the failing step in isolation
Safety burden Needs sandboxing, gating, iteration ceilings, review Blast radius is whatever you wired up

The failure signature to recognise: an agentic system that goes wrong usually does not crash. It returns a confident, well-formed, partly-unfounded answer. Budget for detection, not for exception handling.

Common misclassifications

Sounds like an agent because…But
"It makes five LLM calls" Call count is not agency. Five calls you sequenced is a chain
"It uses tools" A single call with retrieval is an augmented LLM, not an agent
"It runs over 5,000 documents" A for loop over independent calls is batch processing
"It picks between three prompts" That is routing. The model classifies; your code branches
"It retries until the output is good" Evaluator–optimizer. You fixed the cycle; the model fills it
"It has a loop" Only agentic if the model decides whether the loop continues

Arguing it in the room

  1. Concede capability, contest fit. "An agent can do this. Here is what it costs versus the version we can test."
  2. Quantify one axis. Measure tokens or p95 on the real task. One measured ratio beats any amount of opinion.
  3. Name the switch trigger. "Ship the router; if the fallback bucket passes 15% of traffic, we escalate to an agent." Proposes an experiment instead of winning a debate.
When the agent is right, say so plainly

Agents earn their cost on open-ended problems where the number of steps cannot be predicted and no fixed path can be hardcoded. When that is genuinely true, a workflow cannot do the job at any price, and the cost argument is irrelevant — do not hedge.

Anthropic's three implementation principles

  1. Simplicity. Maintain simplicity in the design.
  2. Transparency. Explicitly show the agent's planning steps.
  3. A crafted ACI. Design the agent–computer interface with the same care as a human UI: thorough tool documentation and testing.

Principle 3 is the whole of Lesson 03. The tool schema is the model's entire view of what it can do.

LLM Judge Reference

The build order, the prompt rules, and the two numbers a judge has to report before anyone should trust it. This card continues the evals card: that one covers graders code can run, and this one covers the grader you have to calibrate.

Reference 09· Evals, part 2: model-based grading· Verified 2026-09-22

When to reach for one

“Choosing deterministic graders where possible, LLM graders where necessary… and using human graders judiciously for additional validation” (Anthropic). Use a judge when the property is about meaning: honesty, tone, faithfulness, whether the reply answered the question. If you can write it as a regex, a file check, or a tool-call check, write it as code.

Build order

  1. Label first. Read real outputs. Give each a pass/fail verdict and a critique. Your criteria will change as you go (criteria drift, Shankar et al.), and that's expected.
  2. Baseline. Score an always-pass judge against your labels. Any real judge has to beat it on TPR.
  3. Write the prompt from the critiques. One property, binary verdict.
  4. Run it, then read every disagreement. Decide who was wrong. Fix the prompt or the label, whichever was actually wrong.
  5. Hold out a test set. Report the final numbers on labels the prompt was never tuned against.
  6. Re-calibrate periodically. “LLM-based rubrics should be frequently calibrated against expert human judgment.”

Prompt rules

BinaryPass/fail, not 1–5. Adjacent scale points are “subjective and inconsistent across annotators” (FAQ).
One property“A separate judge for each type of failure.”
Reason, then verdictPut the critique field before the verdict field. “Ask the LLM to reason first before producing an evaluation score” (Claude docs).
Detailed rubric“Vague rubrics produce inconsistent judgments.” Write it from your critiques.
A way outOptionally allow “Unknown” “when it doesn't have enough information” (Anthropic). Count Unknowns separately.
Different modelGuards against self-enhancement bias. Also watch for position and verbosity bias (Yan).

TPR and TNR trade off against each other. “If failures are rare, even a small false-alarm rate can create a lot of unnecessary reviews.” Decide which matters more from what a missed failure costs.

How many labels

About 30 is enough to discover failure modes. To validate a judge: “about 100 examples per failure mode, with enough Pass and Fail examples to measure both classes. Below 60 examples, the confidence intervals are often too wide” (Husain).

The sentence for a design review

“On n hand-labelled cases (f fails), held out from tuning, the judge caught x/f failures (TPR) and wrongly flagged y/p good outputs (TNR = …). The caveat is …” Always give n, both rates, and whether the numbers come from held-out data.
